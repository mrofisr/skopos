# B-02: 10k-series profile and ranked bottleneck report

- Date: 2026-11-15
- Dataset: `test/scale` 10k profile, 6 h range, 60 s step
- Gateway: `test/bench` image, admission 16 in-flight / 32 queued, pprof on
- ClickHouse: 26.8.36.3, `test/bench` Compose service
- Host: 4 vCPU / 7.8 GiB reference host
- Dataset hash: `202641d15fe61544` (seed 42)
- Inputs: 10,000 sum series, 10 services, 3.6M metric rows, 3,600 histogram
  rows, 10,000 logs, 10,000 spans

This report is the B-02 deliverable from
[ADR 0006](../adr/0006-beta-gate.md). The micro-tickets are
[#19](https://github.com/mrofisr/skopos/issues/19),
[#20](https://github.com/mrofisr/skopos/issues/20), and
[#21](https://github.com/mrofisr/skopos/issues/21).

```sh
  --url http://127.0.0.1:18124 --database otel

  --iterations 30 --skip prom_range_6h \
  --json-out /tmp/b02-sequential.json

  --concurrency 30 --duration 60 --warmup 1 --skip prom_range_6h \
  --docker-stats --docker-containers $CONTAINERS \
  --json-out /tmp/b02-concurrent.json
```

The 6 h range query was measured separately because it fails at the default
limits; skipping it keeps the rest of the workload measurable.

## The 6 h range query

`sum(rate(http_requests_total[5m]))` over 6 h at 10k series returns HTTP 500.

```text
Code: 396. DB::Exception: Limit for result exceeded, max rows: 100.00
thousand, current rows: 101.69-104.96 thousand. (TOO_MANY_ROWS_OR_BYTES)
```

The Fetch scan cap is 200,000 rows and the ClickHouse result cap is 100,000,
so the limits disagree. A raw-sample range fetch would need 3.6M rows. The
gateway should return an explicit 4xx for this budget, and the long-range
path needs aggregation pushdown or a rollup.

## Ranked causes

1. **`/api/v1/series` raw-sample fetch.** 1.12 s p95 sequential, 12.6 s p95
   at 30 clients, 24% 503s, 142 KB response. `chclient.Query` is 66% of CPU;
   `labelsKey` is 21% of allocations. The metadata endpoint must not fetch
   samples. [#19](https://github.com/mrofisr/skopos/issues/19)
2. **Range result limit and the 500.** Code 396 at the 100k result cap while
   the scan cap is 200k; a 6 h query at 10k has no defined outcome. Make the
   budget explicit and add aggregation pushdown or a rollup.
   [#20](https://github.com/mrofisr/skopos/issues/20)
3. **Label-values sample scan.** 241 ms sequential, 3.5 s at 30 clients; about
   1M `otel_metrics_sum` rows for 150 bytes of values, with `GROUP BY` and
   `FINAL`. Remove `FINAL` for metadata, cache, or use a catalog.
   [#21](https://github.com/mrofisr/skopos/issues/21)
4. **Shared saturation and admission.** The gateway peaks at 3.1 cores and
   2.4 GiB; ClickHouse at 2.4 cores. The fixed 16/32 admission limit sheds
   8.75% of the mixed workload. The cost model and adaptive limit follow
   B-04 once the metadata paths are fixed.
5. **JSON decode and allocation.** 37.9 GB allocated in 30 s. Fixing #19
   removes most of it; a streaming decode is the next candidate if the
   instant and range paths still dominate after that.

## What this means

The 560-series 50-VU result does not transfer to 10k series. The beta gate in
ADR 0006 is correctly placed: at 10k, the gateway is over capacity at 30
clients, with the metadata paths and the raw-sample fetch as the measured
causes.

the dataset hash pins the input.
