  `ReplacingMergeTree` schema with `FINAL` sample reads
- Host: k0s lab `oracle-cloud`, aarch64, 4 vCPU / 24 GiB
- Dataset hash: `b900affe5ce4b9ec` (seed 42)
- Inputs: 100,000 sum series, 50 services, 36,000,000 metric rows, 18,000
  histogram rows, 100,000 logs, 100,000 spans
- Dataset end: `2026-11-16T01:38:40Z`; the benchmark ran at 00:57–00:59Z

## Setup

The 100k profile is ten times the B-02 series count and row count:

```sh
go run ./test/scale/cmd/scale-gen \
  --profile 100k --range 6h --step 60s --batch 50000 \
  --now 2026-11-16T01:38:40Z \
  --url http://127.0.0.1:18124 --database otel

# The metrics table took 64 s to optimize; the other tables were immediate.
OPTIMIZE TABLE otel.otel_metrics_sum FINAL

go run ./test/bench \
  --base-url http://127.0.0.1:18081 \
  --iterations 30 --warmup 3 --skip prom_range_6h \
  --json-out /tmp/b03-sequential.json

go run ./test/bench \
  --base-url http://127.0.0.1:18081 \
  --concurrency 30 --duration 60 --warmup 1 --skip prom_range_6h \
```

telemetry (about 1,800 metric rows and 8,500 OBI spans); the generated dataset
counts above are the workload contract.

## The 6 h range query

`sum(rate(http_requests_total[5m]))` over 6 h returns **HTTP 422 in 69 ms**
before ClickHouse starts the query:

```text
Code: 158. DB::Exception: Limit for rows (controlled by
'max_rows_to_read' setting) exceeded, max rows: 10.00 million,
current rows: 36.00 million. (TOO_MANY_ROWS)
```

A 1 h range has the same outcome: 12.70M rows against the 10M cap. The direct
row count for the 6 h window is **36,000,300**. B-02 returned a 500 at the
result cap; the explicit row budget now rejects the query before execution
with a 422, but the 100k long-range query is still unsupported. The sample cap
is unchanged by #49: metadata reads have their own budget; sample reads keep
10M and `FINAL`.

`replaceRegexpAll(MetricName, ...)`, which cannot use the primary index
(`MetricName` is the second sort-key column). #49 gives this probe its own row
budget so it completes; it does not remove the scan. The 30 s cache bounds the
refresh rate, and the discovery probe averages 52 ms (p95 148 ms).

## Ranked causes

1. **The instant rate query reads an hour of samples.** The metrics sort key
   is `(ServiceName, MetricName, toStartOfHour(TimeUnix), cityHash64(Attributes),
   TimeUnix, hash)`. A 5-minute rate window at 00:xx can only prune to the
   whole 00:00 hour: **6.36M rows / 413 MiB per query**, even though five
   minutes is about 500k rows. One no-load query is 1.1 s. Under 30 clients,
   42 queries read 16.9 GiB and ClickHouse's 2 cores saturate; instant p95 is
   about 10 s.
2. **The metadata refresh scans 36M rows every 30 s.** The normalized-name
   filter cannot prune, and the sum table holds 36M rows. #49 makes the probe
   legal under the row guard, but the refresh still reads the full table
   (2.08 GiB in the run window). A metric catalog or a skippable index would
   remove the scan; the 30 s cache only bounds its frequency.
3. **Label values and series scan one hour of labels.** `service_name` values
   with no selector read up to 12.7M rows; the filtered series query reads
   270k rows and returns 286 KB at 1.33 s p50 / 1.89 s p95. This is much
   better than B-02's raw-sample fetch, but the label paths still scan the
   hour.
4. **The sample row budget rejects the long range.** A 1 h range needs 12.7M
   rows and a 6 h range needs 36M; the default cap is 10M. The early 422 is
   explicit, but the long-range query has no path at 100k. This needs a B-04
   budget decision (raise the cap, add a projection or rollup, or keep the
   4xx and document the limit).
5. **Count-based admission does not bind at 30 clients.** The lab allows 32
   in-flight, so all 30 clients enter ClickHouse and queue there. A flat
   request count cannot protect a 2-core ClickHouse from 30 expensive instant
   queries; a cost model or per-query concurrency limit is the B-04 candidate.

## B-04 budget candidates

1. **Add a finer metric time prefix or a projection.** Order metric samples
   by `(MetricName, toStartOfFiveMinutes(TimeUnix), ServiceName, ...)` or add
   a projection with that order. Target: an instant rate query reads about
   500k rows instead of 6.36M. Measure the storage delta and the write cost;
   this is the highest-leverage change for the 100k instant path.
2. **Add a metric catalog or a `MetricName` skip index.** A small
   `metric_names` table, or a `set` skip index plus an exact-equality fast
   path, would turn discovery and metadata into a few thousand rows instead of
   36M. Measure the index build time, storage, and the discovery p95.
3. **Decide the sample row budget.** A 20M cap would admit a 1 h range at
   100k but not a 6 h range; a 40M cap would admit both but read 36M rows per
   query. Measure the memory and latency before changing the default. If the
   cap stays at 10M, keep the explicit 422 and document the 100k limit.
4. **Add a cost-aware admission limit.** Weight the instant rate queries by
   their measured cost or cap concurrent rate queries, then rerun the 30-client
   mix. The current 32/64 limit never triggers at 30 clients.
5. **Bound the label-values default range or use the catalog.** A no-selector
   label-values query reads 12.7M rows. Cap the default range, serve
   `__name__` from the catalog, or add a per-hour label rollup.

## What this means

At 100k series the gateway is no longer the bottleneck; ClickHouse's two cores
are. The instant rate path reads one hour of samples because the sort key's
time granularity is one hour, so the 10k gate does not transfer: 69.50 req/s
and 716 ms instant p95 at 10k become 12.57 req/s and about 10 s instant p95 at
100k. The metadata budget fix (#49) is required for any Prometheus request to
succeed at this scale, but it leaves the 36M-row refresh in place. The B-04
budgets should start with the finer metric time prefix and the metric catalog;
the sample row cap and admission model follow from those measurements.
